# OnlineLecture 개발 하네스 설계

## 목적

OnlineLecture MVP 계획을 저장소 안의 실행 가능한 작업 체계로 변환한다. 프로젝트를 처음 보는 주니어 개발자도 한 번에 하나의 작업 카드를 선택해 테스트, 구현, 검증, 커밋까지 완료할 수 있어야 한다. 선행 작업이 없는 카드는 병렬로 진행할 수 있고, 전체 진행 상태는 한 문서에서 확인할 수 있어야 한다.

## 선택한 접근

하네스의 기준 정보는 Git으로 버전 관리되는 Markdown과 소수의 저장소 설정 파일이다. GitHub Issues나 별도 작업관리 애플리케이션은 초기 하네스의 필수 요소로 두지 않는다. 외부 서비스가 준비되지 않은 상태에서도 계획을 읽고 실행할 수 있고, 코드 리뷰에서 계획 변경 이력까지 함께 검토할 수 있기 때문이다.

별도의 상태관리 프로그램이나 생성기는 만들지 않는다. 체크박스, 제한된 상태 값, 의존 작업 ID, 병렬 그룹과 검증 명령으로 필요한 흐름을 표현한다. 자동화가 실제로 필요하다는 증거가 생기기 전까지 Markdown이 단일 진실 공급원이다.

## 문서 구조

- `AGENTS.md`: 모든 작업자에게 적용되는 테스트, 보안, 데이터베이스 migration, 디자인, 커밋 규칙
- `.env.example`: 필요한 환경 변수 이름과 용도. 실제 비밀 값은 포함하지 않음
- `.codex/config.toml.example`: 저장소 범위 MCP 연결 예시와 안전 기본값. 팀이 실제 연결할 때만 `.codex/config.toml`로 복사하며 계정별 식별자와 토큰은 포함하지 않음
- `docs/superpowers/specs/2026-08-02-online-lecture-design.md`: 승인된 제품 요구사항과 기술 설계
- `docs/superpowers/specs/2026-08-02-development-harness-design.md`: 이 하네스의 설계
- `docs/superpowers/plans/2026-08-02-development-harness.md`: 하네스 구축 절차
- `docs/superpowers/plans/2026-08-02-online-lecture-mvp.md`: MVP 전체 단계, 작업 의존성, 완료 조건
- `docs/tasks/README.md`: 현재 단계, 작업 상태, 병렬 실행 가능 묶음과 다음 행동을 표시하는 대시보드
- `docs/tasks/phase-XX/*.md`: 한 명의 구현자가 독립적으로 완료하고 리뷰받을 수 있는 작업 카드

## 작업 카드 계약

각 작업 카드는 셸에서도 안정적으로 검사할 수 있는 고정 YAML front matter를 사용한다. `id`, `title`, `status`, `type`, `depends_on`, `parallel_group`, `owner`, `started_at`, `blocked_reason`, `owned_files`, `shared_files`, `implementation_commit`, `reviewer`, `review_commit` 필드를 같은 순서로 기록한다. 배열은 한 줄 대괄호 형식만 사용하고 값이 없으면 `[]` 또는 빈 문자열로 표기한다. 시각 값은 시간대를 포함한 ISO 8601 형식을 사용한다.

본문에는 다음 정보를 반드시 포함한다.

- 안정적인 작업 ID와 제목
- `blocked`, `ready`, `in_progress`, `review`, `done` 중 하나의 상태
- 선행 작업 ID와 병렬 그룹
- 작업 목적, 범위, 명시적 제외 항목
- 생성·수정·테스트할 정확한 파일 경로
- 이전 작업에서 소비하는 인터페이스와 다음 작업에 제공하는 인터페이스
- 실패 테스트 작성, 실패 확인, 최소 구현, 통과 확인, 관련 전체 검사 순서
- 기능 및 접근성 인수 조건
- 권장 커밋 메시지
- 사람이 확인해야 하는 외부 계정 체크포인트

작업 유형은 `feature`, `migration`, `config`, `docs`, `manual-checkpoint`로 제한한다. `feature`와 동작을 포함한 `migration`은 실패 테스트부터 수행한다. `config`와 `docs`는 구조 검사와 해당 설정의 공식 검증 명령을 사용한다. `manual-checkpoint`는 수행 환경, 증거와 승인자를 기록한다. 작업은 리뷰어가 이웃 작업과 별도로 승인하거나 반려할 수 있는 최소 단위로 나눈다. 단순 설정과 문서는 그것이 필요한 첫 기능 작업에 포함하되, 여러 후속 작업의 공통 기반이라면 별도 기반 작업으로 둔다.

## 의존성과 병렬 실행

마스터 계획은 단계 간 선행 관계를 정의한다. 선행 작업이 모두 `done`인 카드만 `ready`가 될 수 있다. 같은 `parallel_group`에 속하고 서로 파일 소유권이 겹치지 않는 `ready` 카드는 병렬로 실행할 수 있다.

병렬 작업은 `owned_files`가 겹치지 않아야 한다. `package.json`, lockfile, 라우트 및 barrel export, 공용 스키마, migration 번호, 테스트 설정과 환경 변수 파일은 `shared_files`로 분류한다. 공유 파일은 선행 기반 작업 또는 병렬 작업 뒤의 통합 카드 하나만 수정한다. 작업 시작자는 카드 상태를 `in_progress`로 바꾸고 작업자 이름을 적어 중복 작업을 방지한다.

## 진행 상태 관리

`docs/tasks/README.md`가 사람이 읽는 진행 대시보드다. 단계별 완료 수, 현재 `in_progress`, 리뷰 대기, 차단 원인, 즉시 시작 가능한 작업을 표시한다. 각 작업 카드의 front matter가 원본이고 대시보드는 상태 변경 커밋에 함께 갱신한다. 검사기는 대시보드에 모든 작업 ID가 정확히 한 번 나타나는지 확인해 수동 갱신 누락을 차단한다.

작업 생명주기는 다음과 같다.

1. 선행 작업 미완료: `blocked`, `blocked_reason: dependency`
2. 모든 선행 작업 완료: `ready`
3. 작업자가 담당하고 첫 상태 커밋 생성: `in_progress`
4. 구현과 필수 검증 완료: `review`
5. 리뷰 지적 해결과 관련 전체 검사 완료: `done`

외부 계정은 `blocked_reason: external`, 제품 결정은 `blocked_reason: decision`을 사용한다. `blocked` 카드에는 본문에 차단 상세와 해제 조건을 기록한다. 다른 상태의 `blocked_reason`은 빈 문자열이어야 한다.

상태를 `in_progress`로 바꿀 때 `owner`와 시작 시각 기록은 필수지만 상태 전용 커밋은 선택이다. `review`에는 `implementation_commit` SHA를, `done`에는 이를 유지하면서 작업자와 다른 `reviewer` 및 승인한 `review_commit`을 기록한다. 한 사람이 구현과 최종 승인을 동시에 수행하지 않는다.

## 공통 작업 규칙

- 기능과 버그 수정은 실패 테스트부터 시작하고 실제 실패를 확인한다. 문서·설정·수동 체크포인트에는 카드 유형별 검증 계약을 적용한다.
- DB 변경은 `supabase/migrations`의 새 SQL migration으로만 수행한다. 적용된 migration을 수정하지 않는다.
- 브라우저에 서비스 역할 키나 서버 전용 비밀을 노출하지 않는다.
- 공식 shadcn 레지스트리 외의 UI 코드를 설치하지 않는다.
- 디자인 토큰, 키보드 조작, 명시적 라벨, 44px 터치 영역과 WCAG AA 대비를 지킨다.
- 관련 테스트가 통과한 작은 논리 단위마다 커밋한다. 상태만 바꾸는 시작 커밋은 선택 사항이고, 구현 없는 형식적 커밋은 강제하지 않는다. 계획 경로 변경이 필요하면 카드 갱신 커밋과 구현 커밋을 분리할 수 있다.
- 다른 작업자의 변경을 되돌리거나 관련 없는 파일을 포맷하지 않는다.
- 실제 키, 계정 ID, 사용자 데이터와 생성된 다운로드 URL을 커밋하지 않는다.

## 검증 전략

하네스 자체는 추가 런타임 의존성 없이 검증한다. 저장소 파일과 Markdown 링크가 존재하는지, 작업 ID와 허용 상태 값이 일관적인지, 모든 선행 작업 ID가 실제 카드와 연결되는지 확인하는 작은 셸 검사를 제공한다. 제품 구현이 시작되면 공통 완료 명령은 `lint`, `typecheck`, 단위 테스트, Playwright E2E, production build다.

각 카드의 검증은 가장 좁은 테스트에서 시작해 관련 테스트, 공통 완료 명령 순으로 확대한다. Google OAuth 공급자 승인, 실제 YouTube 재생, Resend 이메일 도착과 Supabase Advisor 결과는 배포 환경의 수동 체크포인트로 유지한다.

## 오류와 변경 처리

검증이 실패하면 카드를 `review`나 `done`으로 전환하지 않는다. 작업 계획의 경로나 인터페이스가 실제 코드와 달라졌다면 구현자가 임의로 우회하지 않고, 같은 커밋에서 카드와 마스터 계획을 실제 구조에 맞게 갱신한다.

범위 변경은 제품 설계, 마스터 계획, 관련 작업 카드 순으로 반영한다. 이미 완료된 작업을 무효화하는 변경은 새 작업 ID로 후속 카드를 추가해 이력을 보존한다.

## 완료 조건

- 승인된 전체 MVP 설계가 저장소에 보존된다.
- 모든 MVP 요구사항이 하나 이상의 작업 카드 또는 명시적 배포 체크포인트에 연결된다.
- 각 카드에 선행조건, 상태, 검증, 커밋 경계가 있다.
- 대시보드에서 현재 단계와 다음 실행 가능 작업을 확인할 수 있다.
- 병렬 실행 가능한 작업과 파일 충돌 위험이 명시된다.
- 공통 규칙과 비밀 관리 원칙이 `AGENTS.md`와 환경 변수 예시에 반영된다.
- 저장소 내 검사 명령이 잘못된 상태, 끊어진 의존 작업과 누락 파일을 탐지한다.
